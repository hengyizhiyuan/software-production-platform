## 2. 总体策略

### 2.1 目标定义：什么叫"可用"

一个普通用户用一句话提出软件需求，Watt 在**无人工救援**下完成：理解 → 澄清（仅在真正需要时）→ 计划 →
生产 → 验证 → 独立保证 → 受控授权 → 集成 → 可下载/可运行的软件；过程中聊天与进度反馈**即时**；遇到模型
随机性失败时，系统内部协作推进而不是报错停止。

验收以 **Golden Journey 套件** 在线上组合版本上的真实运行为准（§6），不以单元测试或隔离资格为准。

### 2.2 不变的底线

身份、来源、版本、契约、权限、效果许可、证据完整性、独立 Guardian 判定保持严格；不伪造证据或授权；
错误接纳为 0 是硬指标。其余（实现方式、模块结构、提示、流程编排、性能架构）都可以改。

### 2.3 三项目共建与版本治理（决定 3）

- 三个仓库使用同名共建分支 `claude/c3-formation-ai-native-convergence`：
  Guardian 从 C3 集成线 `0d7aca95` 起，合入 main 的 3 个文档提交；ECF 从 `5aa4f883` 起，合入 main 的 2 个文档提交。
  旧 main / 功能分支保留不动，产品稳定后再整体合入各自 main。
- Watt 仓库新增 **`owners.lock`**：记录 Guardian、ECF 的确切 commit 与源码摘要；Watt 的镜像构建把锁定的 Owner
  源码**烘焙进同一镜像**（不再依赖宿主机挂载目录），一个镜像 = 一个三项目组合版本。
- 发布门禁：组合镜像必须通过 cross_repository 测试 + 真实契约冒烟（构造真实 `AssuranceRequest`、
  `assemble_context`）才能部署；api、coordinator、worker、tool-host **统一同一镜像**。

## 3. 开发准则（Human 2026-10-15 新增，后续实现必须遵守）

### 准则 A：以产品目标为准重审架构，不合理处可以重构

Watt 的定位是 AI 原生软件研发平台：意图驱动、模型产出候选、Owner 治理接纳、独立保证、自动推进。
审计暴露的结构性问题，按以下方向重构（不是重写）：

| 现状问题 | 重构方向 |
| --- | --- |
| 失败只能 BLOCKED 或问 Human"要不要暂停" | **问题路由成为 Plan Steering 的一等能力**：每个 Owner 失败输出标准交接物（谁该解决、缺什么、可选方向），Steering 路由给能解决它的 Owner（澄清 / 重规划 / 回执行 / 取证 / 问 Human 具体问题） |
| 几乎所有生产阶段跑在 api 进程的线程里，与 HTTP 争用 | **请求路径与生产路径分离**：api 只做交互与投影；Steering/Formation/Verification/Guardian/Preview 编排迁到独立的 production 进程（复用现有 worker 镜像，新增 role），通过数据库队列与事件衔接 |
| Formation 契约版本层层叠加（v1→v4、多个 marker 分支） | 收敛到当前一种表示（按来源重述 + Owner 编译），旧契约只保留读取历史收据所需的兼容代码 |
| Design Intent 关键词框架、WIC 修复指导按错误文本分派 | 由已有 WIC 语义理解提供；修复反馈改为结构化失败谓词 |
| Owner 源码挂载 + 部署脚本写死版本 | `owners.lock` + 单镜像组合版本（§2.3） |
| 恢复服务写好未接线、Attention 类型定义未产出 | 接入问题路由，删除无用分支 |

重构约束：每一步保持可部署、可回归；旧数据可废弃（线上无历史包袱），但新代码不保留伪兼容层。

### 准则 B：全链路性能是产品质量，不是优化项

见 §4。每个阶段的交付物都必须附带性能数据，性能退化视同功能缺陷。

### 准则 C：模块要聪明，并且对模型有自适应能力

- **聪明**：模块理解自己的目标，而不只是执行检查；失败时知道失败在哪、该谁补；
  遇到歧义会澄清而不是猜；能用结构化反馈让下一次尝试更好。
- **模型自适应**：强模型时高效直达；弱模型时系统用机制补足能力，逼近强模型的结果。具体机制见 §5。

## 4. 性能建设方案

### 4.1 现状数据（线上 api 72 小时请求日志，只读统计）

| 场景 | 实测 | 主要耗时来源 |
| --- | --- | --- |
| 首页 `GET /api/experience/home` | p50 **2.6 s** | 每次请求 **42 次 git 子进程**、**221 次数据库查询**、48 次投影计算，投影累计 4.2 s |
| 集合页 `GET /collections/{kind}` | p50 2.6 s | 同上 |
| 工作区 `GET /products/{id}/workspace` | p50 446 ms，p95 690 ms；**被前端每 2.6 s 整页轮询** | 83 次数据库查询 + 投影 665 ms |
| 首次意图 `POST /experience/intent` | 3.9–4.8 s | 模型调用在**请求内同步**执行（≈4 s），期间用户无任何反馈 |
| 聊天 Turn 处理 | 排队 | `InteractionService` 的 Turn 执行器 **`max_workers=1`**：全系统所有用户、所有 Turn 串行处理 |
| 聊天回复显示 | 2.6 s 轮询粒度 | 新版前端 `experience.js` 用 2.6 s 定时整页重绘；已有的 SSE 流接口只有旧前端 `app.js` 使用 |
| Formation | 每次 ≈90k 输入 token，2 候选 + Review 串行 4 次调用，单次 18–60 s | 每次请求重复发送完整库存、全部前置条件与长指令 |
| Verification | 单请求最高 **350k 输入 token** | 全量上下文直接塞给模型 |
| Native 执行 | 一次 G0 ≈446k token | 合同、历史收据重复注入（已部分压缩） |
| 生产链编排 | 阶段间轮询（Orchestrator 每秒轮询），全部在 api 进程线程内 | 与 HTTP 请求争用 CPU/GIL/连接池 |

### 4.2 原则

1. **先测量后优化**：统一的阶段耗时与 token 观测（已有"请求性能"日志扩展到生产阶段与模型调用），每个 Golden Journey 输出逐段时间线。
2. **用户感知优先**：聊天首字节 ≤1 s、进度事件实时推送，比总时长更重要。
3. **请求路径零阻塞**：HTTP 请求内不做模型调用、不做 git 子进程、不做重投影。
4. **少即是快**：模型调用的上下文做减法（按需、差量、缓存前缀），比换更快的模型更有效，也直接减少 token 浪费。
5. **并行而非串行**：无依赖的模型调用与 Owner 检查并发执行。

### 4.3 具体措施

**P-1 交互实时化（聊天卡顿）**
- 意图与 Turn 一律异步受理：`POST` 立即返回 turn id（<200 ms），模型处理在后台进行；
- 新前端改用已有的 SSE 流（`/api/interactions/{id}/turns/{turn}/events`）流式显示回复，删除 2.6 s 整页轮询；
- Turn 执行器从全局 `max_workers=1` 改为**按交互串行、跨交互并行**（每个对话保持顺序，不同对话并发）；
- 先流式返回对话回复，语义解析（WIC_SEMANTIC）与之并行，而不是串行在回复之前。
- 目标：首字节 ≤1 s，回复流式完成；Turn 受理 p95 ≤200 ms。

**P-2 读路径投影（页面卡顿）**
- 首页/集合/工作区改为读取**持久化的读模型**（事件驱动更新的投影表），不在请求中执行 git 子进程和重投影；
- git 派生信息（版本、文件树）在写入时计算并缓存，按 commit id 永久缓存；
- 工作区改为 SSE 推送变化，前端按事件局部更新。
- 目标：首页 p95 ≤300 ms，工作区 p95 ≤150 ms，查询数下降一个数量级。

**P-3 生产链事件驱动（任务执行反馈卡顿）**
- 生产编排迁出 api 进程（准则 A），阶段之间用数据库队列 + `LISTEN/NOTIFY` 事件衔接，取代秒级轮询；
- 每个阶段开始/结束/进度发布统一的 Work 事件流，前端实时显示"正在做什么、预计多久、为什么"；
- Preview 构建、Verification、Guardian 等无依赖步骤并行。

**P-4 模型调用做减法（Formation / Verification / Native 慢且贵）**
- **稳定前缀 + 差量**：把指令和不变的库存放在请求前部以命中 Provider 前缀缓存；修复请求只发送失败相关的部分（按来源重述已经让修复只需处理受影响来源）；
- **按需上下文**：Verification 只发送被检查义务相关的源码片段与 Fact，而不是全量；Native 合同历史引用化（已有）推广到其余阶段；
- **确定性先行**：能由 Owner 确定性判定的（身份、覆盖、引用、重复）在调用模型前完成，模型只做语义部分；
- **结果缓存**：相同输入指纹的语义判断（例如同一库存的理解、同一组件的 Review）复用。
- 目标：Formation 单次输入 token 降 50% 以上；Verification 单请求 ≤60k；一次普通需求全链路 token 降一半。

**P-5 观测与门禁**
- 每个 Golden Journey 产出逐段时间线（等待 / 模型 / 数据库 / git / 子进程），作为发布门禁的一部分；
- 设定性能预算，超出即视为回归。

### 4.4 性能目标（首轮）

| 指标 | 现状 | 目标 |
| --- | --- | --- |
| 聊天首字节 | 4–5 s（且不流式） | ≤1 s，流式 |
| 首页 / 集合页 | 2.6 s | ≤300 ms |
| 工作区刷新 | 446 ms + 2.6 s 轮询延迟 | ≤150 ms，事件推送 |
| 进度可见性 | 轮询，阶段内无反馈 | 阶段事件实时推送 |
| 普通需求意图 → 可下载 | 当前无法跑通 | 跑通，并持续下降（首轮记录基线） |
| 普通需求全链路 token | ≈1M+ | 降 50% |

## 5. 模型自适应智能

### 5.1 能力分层，而不是写死一个模型

为每个模型调用点声明**所需能力**（理解、结构化输出、长上下文、推理深度），由 Model Runtime 按配置的
模型档位选择具体模型与参数。系统记录每个档位在每个调用点的真实表现（接纳率、修复次数、耗时、token），
作为调度依据。

### 5.2 强模型：高效直达

- 单次完整候选、宽松的预算上限内一步完成；
- 减少分解与中间校验调用；
- 推理开关按调用点需要打开（如 Formation 语义选择），简单步骤关闭。

### 5.3 弱模型：用机制补足

在**同一套 Owner 门禁**下，用以下机制提升弱模型的有效能力（只改变"怎么生成"，不改变"什么可以接纳"）：

| 机制 | 作用 | 已有基础 |
| --- | --- | --- |
| 确定性前置与编译 | 把编码、记账、身份、跨度、引用交给 Owner，模型只做语义选择 | 本周的按来源重述 + 标点编译 |
| 任务分解 | 把大任务拆成小的语义决策（逐来源、逐组件），每步输入小、目标单一 | Formation 已按来源组织 |
| 结构化可行动反馈 | 失败谓词 + 影响范围 + 可选方向，而不是错误码 | Verification / Formation 已部分具备 |
| 多样本 + 一致性 | 关键语义决策采样多个候选，用确定性校验与一致性投票选择；分歧本身作为歧义信号交给澄清 | 现有候选/Review 结构可承载 |
| 自检与独立复核 | 生成后由同一或另一模型按结构化清单复核，复核意见作为修复输入 | Trace 自审、Formation 独立 Review |
| 示例与模式记忆 | 已被接纳的同类结果（经治理接纳的历史 Projection、计划、修复）作为少样本示例 | 历史收据可提供 |
| 升级 | 弱模型在同签名上无进展时，单步升级到强模型完成该步 | Work 级收敛已能识别无进展 |

### 5.4 验证方式

同一 Golden Journey 套件分别在强、弱两个模型档位上运行，比较可用率、耗时、token：
强档以"快和省"为目标，弱档以"接近强档可用率"为目标。两档错误接纳均为 0。

## 6. 对话智能与引导式开发（Human 2026-10-15 补充）

### 6.1 准则 D：回复要聪明，充分识别并理解用户意图

WIC 交互智能 2026-09-22 已通过 Human 验收（意图贴合、问题更少更有价值）。继续优化的依据是代码中仍存在、
会让回复"显得笨"的结构性原因（已核对）：

| 现状 | 位置 | 影响 |
| --- | --- | --- |
| 负责措辞的 Realizer **看不到用户本轮原话**：信封 `latest_human_input=None`，最近消息只取 COMPLETED，当前消息正处于 PROCESSING 被过滤 | `wic_response.py:549`、`interaction.py:1763-1765` | 回复像在回应"状态"而不是回应"你刚说的话" |
| 多类场景由**确定性模板覆盖**模型措辞："你想…。我建议：…"、"新增约束已纳入：…"、"已记录当前约束：…"、"当前目标已准入生产 Work：…" | `wic_response.py:680-797`、`interaction.py:1828-1851,2445,2460` | 机械、重复、像表单回执 |
| 门禁过紧：问题预算默认 0，超额问句逐句删除；任何大写下划线词视为术语泄漏并重试；两次失败给兜底句"当前说明暂时无法安全展示" | `response_contract.py:469-627`、`wic_response.py:246-330`、`human_language.py:4` | 话说一半、该问不问、偶发莫名兜底 |
| 语义阶段约 430 行以规则为主的指令 + flash/low 推理 | `interaction_contract.py:534-960`、`config.py:121-135` | 注意力被规则挤占，理解深度不足 |
| 全局单线程 Turn 执行、2.6 s 轮询、不流式、不渲染 Markdown | `interaction.py:741`、`experience.js:46-47,211` | 慢，进一步放大"笨"的观感 |

要求：
1. 回复必须直接回应用户本轮原话与真实意图，并体现对产品/Work 上下文和先前对话的记忆；
2. 模板只用于安全兜底，不用于常规表达；事实、权限、状态仍由治理层提供，但措辞交给模型；
3. 问题要有价值：先给出理解与建议，再在真正需要时问最关键的一个；不为凑格式提问，也不吞掉必要的问题；
4. 对模型档位自适应（§5）：理解与措辞两步按调用点能力选择模型与推理强度。

### 6.2 准则 E：引导式开发，但不强流程阻断

Watt 既能一句话开工，也能像资深架构师一样引导用户把模糊需求具象为完整方案：

1. **方案框架**：根据诉求生成"设计方案框架"（目标、用户与场景、功能范围、关键约束、技术形态、验收标准等，按领域自适应，不套模板），持续展示在工作区；
2. **把控节奏**：每轮聚焦一个最有价值的议题，给出建议方案与理由，用户确认、修改或让 Watt 决定；已定事项沉淀为方案事实；
3. **主动询问开工**：当重要议题都已确定时，Watt 主动提出"方案已具备开工条件，是否开始实施？"并列出将要做什么、系统代为决定了什么；用户同意后进入实施；
4. **随时可开工**：工作区始终提供"以当前方案进入生产"。点击后：
   - 依据已取得的方案事实生产；
   - **重要缺失点**（影响结果、不可安全默认、涉及权限/范围/价值取舍）停下来问用户，一次问清；
   - **不重要的缺失点**系统自行决定，并记录为"Watt 代为决定"清单；
5. **事后可改**：用户对结果或代为决定的事项不满意，直接提出修改意见，作为新的 Work 修订进入生产，不需要重走设计流程。

### 6.3 实现思路

**对话智能（D）**

| 改动 | 说明 |
| --- | --- |
| 把用户本轮原话、最近对话（含当前消息）放进 Realizer 输入 | 最小且收益最大的修正 |
| 理解与回复合并/并行 | 非生产 Turn 走"单次调用：理解 + 流式回复"；涉及生产/权限的 Turn 先流式给出自然回应，治理语义并行完成后再补充确认 |
| 模板退为兜底 | 事实、约束、状态以结构化字段提供给模型，由模型组织语言；只在模型失败时使用模板 |
| 门禁改为"修正而不是删除" | 问题预算由语义层的真实缺口决定；问句超额或术语泄漏时把具体问题反馈给模型修改一次，而不是逐句删除或兜底 |
| 指令瘦身 | 把以规则为主的长指令拆成"理解目标 + 少量硬约束"，其余规则由 Owner 确定性校验承担（同 Formation 的做法），把模型注意力留给理解 |
| 模型档位 | 理解步骤用推理档；措辞步骤用快速档；弱模型时启用自检（回复是否回应了原话、是否有空话） |
| 评测 | 建立对话 Golden 集（模糊需求、补充约束、纠正、闲聊、状态询问、跨领域），用独立评审模型按"是否理解意图、是否有用、是否啰嗦/机械"打分，作为回归门禁 |

**引导式开发（E）**

复用已有基础：IRK 的 GUIDANCE_REQUIRED（建议 + 一个问题 + 接受建议）、缺口分级 MATERIAL_OUTCOME /
SAFE_DEFAULT / ROUTINE_HOW、Guided Design 的议程与 readiness 模型、Work 修订接口。

| 改动 | 说明 |
| --- | --- |
| 方案框架前移到准入之前 | 当前 Guided Design 议程只在 Work 准入后启用，准入前的"设计指引"是固定取第一项、"0 of N"的占位。改为在对话阶段由 WIC 语义 + Guided Design 议程实时计算方案框架与各议题状态（已定 / 建议中 / 待定 / Watt 代为决定），挂在对话的共享理解上 |
| 议题生成语义化 | 议程不再由固定 Schema 套用，由模型按诉求与领域生成，Owner 校验结构；Design Intent 关键词框架移除（准则 A） |
| 开工判断改为"先问" | 当前 READY 后 `production_admission.prepare` 自动准入。改为：READY 时产出"建议开工"，回复中列出实施要点与代为决定事项并询问；用户同意后沿用已有的接受建议路径准入 |
| "以当前方案进入生产" | 新增接口（如 `/api/interactions/{id}/proceed-with-current-plan`）与工作区按钮：未定的 SAFE_DEFAULT/ROUTINE_HOW 由 Watt 按建议决定并写入 Work 约束与假设清单；MATERIAL_OUTCOME 缺口汇总成一次提问（Attention），用户回答后立即开工；无重要缺口时直接准入 |
| 代为决定清单 | 每个代为决定项保留理由与依据，作为 Work Reality 的显式假设展示；用户可在工作区直接改，改动作为 Work 修订进入生产 |
| 前端方案面板 | 不新增面板。引导式方案并入四象限左上"设计文档/代码"（见 §6.4） |

### 6.4 工作区四象限（Human 2026-10-15 订正，坚持此设计）

工作区采用 Human Governor 的四象限设计，订正此前的语义漂移（2×2 位置保留了，但各象限内容被改成了
"计划 / 现状 / 待你处理 / Watt 正在做"）。权威定义同步写入
[Workspace-first 原则 §11](../product/workspace-first-experience-principles.md#11-workspace-four-quadrant-invariant)：

| | 左 | 右 |
| --- | --- | --- |
| 上 | **设计文档 / 代码**：开工前展示引导式方案框架（议题与状态、当前讨论焦点、Watt 代为决定清单、"以当前方案进入生产"按钮）；开工后展示形成的设计文档与代码（文件树、Diff、预览入口） | **执行 Agenda**：Plan Steering 的执行议程——阶段与步骤、当前所处位置、下一步做什么与为什么；问题路由引起的重规划在此体现 |
| 下 | **生产状态**：Executor 实时执行信息（当前 PWU、步骤、工具活动、进度、恢复）与 Guardian 执行信息（检查中、判定、Findings、修复进度），SSE 实时推送 | **人工操作**：只放真正需要 Human 介入的事项及其操作按钮——重要缺失点提问、受控授权的撤回、凭据/权限、验收 |

订正要点：
- 下排两个象限位置互换（Human Governor 2026-10-15 明确批准）：生产状态在左下、人工操作在右下，使用起来更顺手；只换位置，不改语义；
- 代码资产回到工作区（左上），不再只是外部链接页；
- 原"现状"象限的状态清单拆解：执行进度归"执行 Agenda"，Executor/Guardian 归"生产状态"，结果归"设计文档/代码"；
- Guardian 从"一行状态"变为生产状态中的完整执行信息；
- 对话保持在网格之外，与四象限联动；窄屏按 设计文档/代码 → 执行 Agenda → 生产状态 → 人工操作 堆叠；
- 结构性变更仍需 Human Governor 明确批准；现有四象限结构测试按新语义更新。

### 6.5 对话框位置与交互（恢复既有设计，Human 2026-10-15）

恢复 [Core Workspace Experience Calibration Notes §18 与 §21.2](../product/watt-core-workspace-experience-calibration-notes.md#18-transient-current-interaction-layer)
已批准、但正式界面未落实的交互设计（原型记录见
[v2.2 交互校准](../evidence/watt-clickable-human-experience-prototype.md#v21--v22active-work-与当前交互归属校准)；
原型不代表正式界面已实现）：

| 部分 | 设计 |
| --- | --- |
| 输入框（Composer） | 固定属于中央工作区底部、四象限之下。空闲时是一行停靠栏；聚焦时在同一底部锚点向上展开；发送后收回。右侧历史区**不放**主输入框或伪输入控件 |
| 刚提交的输入 | 发送后仍显示在中央、靠近输入框，方便回看原话并与 Watt 的理解对照；视觉上次于 Watt 回复与工作区事实 |
| Watt 当前回复 | 在中央 Current Interaction 区**流式**显示，与本轮输入共同保留；不让用户转向右侧历史阅读 |
| 历史对话区 | 位于右侧，作为次要但持续可用的历史与来源记录，降低视觉权重 |
| 归入历史（安静过渡） | 回复完成后保留阅读宽限期；悬停、键盘聚焦、选中文字或手动展开时暂停归档；保护结束后中央这一轮淡出、右侧对应内容淡入（轻微透明度/位置/模糊变化，无飞行轨迹）；每条消息按原顺序进入历史且只出现一次；下一轮先开始时，上一轮先归档再显示新一轮 |
| 长回复 | 限高、局部滚动、显式展开，不长期遮挡工作区 |
| 对话消散，事实保留 | 归档后由该轮对话带来的真实变化仍留在四象限：约束/方案变化在"设计文档/代码"，下一步变化在"执行 Agenda"，所需决定在"人工操作"，受影响执行在"生产状态" |
| 减少动效偏好 | 尊重 `prefers-reduced-motion`，改为无位移的干净状态切换 |
| 统一身份 | 只有一个 Watt 身份，不引入吉祥物或第二助手 |

具体宽限秒数等时序是校准参数，不是产品规则。实现与 P-1 流式交互（§4.3）同步完成，SSE 直接驱动中央 Current Interaction。

### 6.6 界面风格（Human 2026-10-15）

本次重构同时更新 UI 视觉层：**简洁、线条纤细、配色高雅**，对齐当下 AI coding 产品的设计趋势。

- 大量留白、清晰层级；以细线（1px 低对比分隔线）和轻微层次代替厚重卡片、粗边框与大面积色块；
- 克制的中性色底（浅色与深色两套主题），单一低饱和强调色用于焦点与主操作，状态色（成功/警示/错误）低饱和、小面积使用；
- 现代无衬线界面字体 + 等宽字体用于代码、路径、标识；字号层级少而稳定；
- 动效短而安静（淡入淡出、轻微位移），服务于连续性而非装饰，遵守减少动效偏好；
- 代码、Diff、执行日志采用编辑器式呈现，信息密度高但不拥挤；
- 四象限、Composer 与历史区的结构语义（§6.4、§6.5）不受视觉调整影响。

实现方式：在现有 [Appearance Architecture / Skin Library](watt-formal-ui-appearance-and-skin-library.md) 中新增一套设计令牌（颜色、线宽、圆角、间距、字体、动效）作为新的默认工作区外观，取代当前 `INDUSTRIAL_CYAN` 默认；旧外观保留为可选皮肤或移除（线上无历史包袱）。

授权仍走受控授权（决定 4）：用户点击开工或同意建议即构成意图授权；Guardian PASS 与全部门禁通过后由系统按策略授权
Candidate，用户可随时撤回。

## 7. 执行路线图

每个阶段都在**线上组合版本**上以 Golden Journey 套件验收，并附性能时间线。

**Golden Journey 套件（首版）**
1. 最简网页需求（"创建一个网页，包含按钮，点击弹出 hello Watt"）；
2. 普通 G0（静态页 + 精确标题段落 + 排除约束，即 ordinary34/41 同类需求）；
3. Brownfield 小改动（在已有仓库首页加一个链接）；
4. 含歧义需求（如"新增一个关于页"，需要澄清范围）；
5. 引导式设计：模糊需求（如"我想做一个团队用的小工具"）经方案讨论具象化后主动询问开工；以及中途点击"以当前方案进入生产"；
6. 构造失败场景：Formation 耗尽、Guardian BLOCKED、ECF 上下文不足；
7. 对话 Golden 集（§6.3）：独立评审打分作为回复质量门禁。

| 阶段 | 内容 | 完成判据 |
| --- | --- | --- |
| **M0 三项目共建基线**（约 3 天） | 三仓库共建分支；`owners.lock` + 单镜像组合版本；发布门禁；线上 api/coordinator/worker/tool-host 统一组合镜像；性能观测扩展到生产阶段；跑一次 Golden 1、2 记录逐段断点与时间线 | 线上无混部；契约冒烟通过；一份真实断点表与性能基线 |
| **M1 交互即时化与对话智能**（约 1.5 周，与 M2 并行） | P-1、P-2：异步受理、SSE 流式、按交互并行、读模型投影；§6.3 对话智能改动；对话 Golden 集与评审门禁；§6.4 四象限语义订正（执行 Agenda、生产状态 Executor/Guardian 实时信息、人工操作）；§6.5 中央 Composer 与 Current Interaction、安静归档到右侧历史；§6.6 新视觉设计令牌 | 聊天首字节 ≤1 s；首页 ≤300 ms；对话 Golden 评分较基线提升 |
| **M2 问题路由与死胡同清零**（约 1.5 周） | W2 交接契约（含 Guardian INSUFFICIENT/ESCALATE、ECF 补齐 Owner）；Steering 问题路由；恢复服务接线；受控授权（决定 4：Guardian PASS + 全部门禁通过后由系统按策略授权并记录，Human 可随时撤回） | Golden 5 的三类失败都被接手；Golden 1、2 无人工走到可下载 |
| **M3 生产链事件驱动与模型调用减法**（约 1.5 周） | P-3、P-4：编排迁出 api、事件衔接、上下文减法、缓存；Formation 契约收敛 | Golden 1–3 全链路耗时与 token 较 M0 基线下降 ≥50% |
| **M4 引导式开发、不确定性一等化与模型自适应**（约 2.5 周） | §6.3 引导式开发（准入前方案框架、先问开工、以当前方案进入生产、代为决定清单，呈现在四象限左上"设计文档/代码"）；歧义澄清闭环；§5 能力分层与弱模型增强 | Golden 1–5 在强档稳定通过；弱档可用率接近强档 |
| **M5 稳定性与泛化**（持续） | Golden 套件重复运行；扩充案例；独立 Holdout 复验（执行者酌情安排时机，复验者保持独立）；三项目合入各自 main | 多轮重复通过；错误接纳 0 |

M1 与 M2 可并行推进：M1 只动交互与读路径，M2 只动生产语义链，冲突面小。

## 8. 工作方式

- 每个里程碑结束：提交、推送、部署线上、跑 Golden 套件、附性能时间线与 token 消耗，简短汇报结论；
- 中途遇到失败先从系统层面判断（是否是共性缺口、该由哪个 Owner 解决），不陷入单案例调参；
- Token：每次真实运行前估算，运行中按调用计数熔断，避免无效重跑；
- 需要 Human 决策的只有：价值/范围取舍、真实外部权限（如云部署凭据）、产品验收。
